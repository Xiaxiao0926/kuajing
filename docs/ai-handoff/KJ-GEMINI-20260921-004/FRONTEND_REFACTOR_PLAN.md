# /kuajing 前端渐进重构策划 V0.1

Codex，2026-09-21；2026-09-22 补录进度。基于 004 审计与独立代码抽查。以 APPROVED_BASELINE.md 校正本地事实；后续局部任务验收以各自 REVIEW 为准，其余阶段仍是候选计划，不是上线授权。

## 一、目标与边界

服务 2–3 人内部选品、采购、核算、立项与跟踪工作：少绕路、容易比较、保存状态可信、电脑手机都能读。不是建设 SaaS，也不做营销首页。
沿用 React/Vite、WordPress 挂载及现有业务存储结构；不拆 /kuajing，不迁移技术栈，不以重构为由重写后端。
原则是“换展示与交互，不换数据身份和计算含义”。现有资料、报告、上传源文件、旧工具及项目必须继续可访问。不能保证未实测的零丢失，必须以保存/恢复证据验收。

## 二、不可破坏清单

| 对象 | 保留要求 | 验收方法 |
| --- | --- | --- |
| 地址与入口 | /kuajing/、短代码、旧 Node ID/别名、已有报告和资源路径 | 新旧入口映射全覆盖；原链接仍打开原资料 |
| 实体 | candidate/project/snapshot/log/costScenario/supplier/quote/sample 的 ID、关联、阶段、版本 | 合成旧/新数据加载前后结构对比，不补写、不重编号 |
| 状态存储 | t6/mi/旧单品 keys、本地 revision/dirty/deleted/device metadata | 读写矩阵、无关键不变、冲突不覆盖 |
| 报告与附件 | 静态 HTML 与生成索引、market-report-sources、market-report-json、上传队列 | 导入源文件与报告能关联、重开可读、断网恢复不丢队列 |
| 计算 | 引擎、费率源、单位/币种/精度、黄金案例 | 同一输入输出一致；npm/golden/sync |
| 保存 | 显式保存、草稿归属、外部冲突、服务器确认与本机保存区分 | A/B 切换、失败重试、关闭/刷新、并发合成测试 |
| 访问及样式 | 现有鉴权、运行配置注入、真实根容器隔离 | 不影响 WordPress 其他页；不改权限和密码 |

不默认新增字段/存储前缀，不把历史工具改为只读，不删除“看似废弃”的数据或文件。

## 三、面向人的页面组织

### 工作框架

- 保留现有八个业务域，先统一术语与入口层级，不另造导航体系。
- 桌面：稳定左导航、紧凑顶部上下文、主工作区。顶部始终可辨“独立核算”还是“某项目”，保存状态就近显示。
- 项目详情：名称/编号/阶段及主要动作保持可见，下方使用既有 Tab；不堆叠多个大卡片和重复标题。
- 报告中心：目录/筛选 + 当前报告，保留切换、导入、源文件关联、历史报告和已有导出方式。报告内容不在换壳中重算或删减。
- 候选/项目列表：搜索、筛选、排序、比较信息集中在紧凑工具栏，减少多层抽屉互相覆盖；从详情返回保留筛选/滚动位置。
- 旧单品工具：可重新分组并说明上下文，但保留现有读写能力。只有确认用户数据用途后，才另行讨论迁移或只读。

### 视觉与可读性

- 沿用现有基础 UI 组件，不新建一套组件库。限定到工作区样式，不改全站主题。
- 正文建议 14–16px，主要工具标题 20–24px，固定字号与合理行高；不用视口宽度缩放字体，不负字距。
- 浅中性背景、深色文字、单一主要动作色，成功/警告/错误按语义区分；不通篇蓝紫渐变，不用装饰性大图。
- 图标按钮使用现有 Lucide 并提供名称；清晰命令保留文字。关键保存与冲突不要仅靠颜色区分。
- 表格数字右对齐，单位写在列名或输入旁；优先保留商品、数值、状态、动作的可读宽度。窄屏采用行摘要+详情或可控横滚，比较后再选，不直接全面卡片化。
- 产品图、原报告图表和证据图保留；设置稳定尺寸、首屏/非首屏加载策略，禁止用假数据或装饰图代替真实产品。
- 空态、加载、失败、未保存、待同步、已同步、冲突都必须可区分；不增加成段“如何使用”的说明文字。

## 四、实施顺序与门禁

### S0 事实与兼容基线（限定范围已完成）

004 Revision 001 经 Codex 校正后有限验收，原交付不作为整体事实合同；003 合同独立待验收，不阻塞无关视觉原型，也不偷偷实施新合规字段。
记录现有代码与 dirty 文件、页面/存储/报告映射，真实线上版本仍标未知。日后上线前核对实际插件能力与接口，而不是强制按本地目录版本升级。
通过标准：主要事实不矛盾、保存链路无关键漏项、每条风险有证据等级。仅规划不需要生产写入。

### S1 保存安全与小范围体验样板

先调查合成项目 A/B 下的核算写入及站内切换丢草稿路径。确认问题后，分别签发最小修复，禁止一次重写所有 Store。
未保存提示须覆盖 Tab、侧栏、项目切换与后续浏览器导航；继续编辑不丢输入，明确放弃才离开。只加 beforeunload 不算完成；不要在组件卸载后才询问。
同时可独立做合规事项窄屏样板，仅调整局部布局、不碰业务处理器。验证后再考虑复制至其他表格。
门禁：已有草稿 A/B/冲突保护回归通过；项目模式不意外写无关全局 key。保留有意共享的费率与用户偏好。

### S2 导航与视觉统一（保留入口）

Hash 深链接是候选方案，先列 route <-> Node/opaque entity ID 映射与浏览器状态规则。不要使用人类项目编号代替 ID，也不要把 private 数据写进 URL。
验收必须包括无 Hash 旧入口、首次加载待鉴权/待同步、未知 ID、删除/不存在实体、非法 Hash、刷新、前进后退、取消离页、Tab 恢复。未知入口显示可返回状态，不新建空项目。
优先现有路由机制或经核实的成熟轻量库；若拟手写路由/加依赖，先提交取舍，不在任务中顺手安装。
统一项目列表/详情和报告中心框架，再逐页调整核算/采购。每批 1–2 页，有前后截图和旧功能检查表。不改变保存格式，不隐藏旧数据入口。

### S3 性能按证据优化

先用匿名合成小/中/大数据集，测首屏可交互、数据加载、筛选响应、DOM 规模、图片请求与资源体积，记录设备/网络/缓存/样本规模。
从低风险项开始：稳定图片尺寸和非首屏懒加载、列表分页/减少无用渲染、报告按需加载、复用已加载数据。测量证实仍有瓶颈才评估虚拟列表或 Worker。
不将几百条数据直接等同于卡顿，不设没有基线的“提速百分比”。性能改进不得破坏筛选、排序、键盘访问、打印和数据完整性。

### S4 本地验收与受控发布（需单独授权）

完成本地功能/视觉/存储兼容测试后，才申请发布。先确认真实现网版本、部署入口、当前 API 能力和恢复证据；不要求为流程形式额外建设 staging/SSH。
源码快照 != 业务备份。上线前对服务器数据与文件用现有授权机制做可恢复备份，核验清单/数量/校验值；不把业务数据推公开 GitHub。
只部署明确变更文件/构件，验证实际版本、资源路径、鉴权、报告读取和保存确认。若需后端升级，拆成独立批准变更。
回滚前端到兼容构件，不用旧数据库覆盖发布后的业务记录；发现 schema/协议不兼容立即停止，由独立方案处理。

## 五、共同验收矩阵

- 视口：360/390/768/1366/1440/1920；先验证完整外壳，再验证具体组件。字体清晰、按钮不竖排、无重叠，横滚仅限必要表格。
- 关键流：报告读取与导入、市场机会到候选、立项与详情、独立/项目核算、供应报价采用、商品/合规保存、阶段推进、历史入口访问。
- 数据流：新旧缺字段数据、项目 A/B、空/长文本、多语言、断网与重新鉴权、403/409/500、存储满、上传排队、恢复失败。合成测试，不写真实生产进行演练。
- 状态语义：界面“已保存”必须明确是本机还是服务器确认；备份失败和读取失败不能伪装为空数据。
- 每次改动保存实际 diff、基线/结果哈希、命令退出码、日志与截图。功能测试和视觉验收分开记。
- 生产修改后跑既有 npm test / test:golden / test:sync，持久化触及时加 test:web-persistence，并明确运行专项浏览器测试；不把环境跳过当通过。

## 六、当前决定

批准方向：保留结构的渐进前端优化；先证据与保存安全，后导航与样式，最后性能。
暂不批准：直接升级生产插件/补库、删除旧入口、全站重写、自动数据迁移、把全部计算器变成纯受控、无性能测量就上虚拟化。
